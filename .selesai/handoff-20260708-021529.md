### Workflow mechanics

Three read-only subagents investigated workflow behavior. Findings:

- Workflow engine is in `src/extensions/workflow/`.
- Core files:
  - `src/extensions/workflow/state-machine.ts`
  - `src/extensions/workflow/adapter.ts`
  - `src/extensions/workflow/modes/prototype.ts`
  - `src/extensions/workflow/modes/quick.ts`
- Registered tools:
  - `start_workflow`
  - `start_quick_workflow`
  - `write_workflow_artifact`
  - `end_workflow`
  - `end_quick_workflow`
- Docs mention a `next` tool, but code does not expose one.
- Workflow advances when expected artifact file exists.
- Semantic completion is not validated.
- Loop/audit cleanliness is prompt-only.
- `write`/`edit` are blocked during active workflow, but `bash` is not blocked.
- Workflow prompt text uses stale `subagent_type`, but real subagent API uses `agent`.

### Main root cause

Current workflow mixes three systems without one owner:

1. State machine: checks phase/file existence.
2. Prompt text: tells model what routine to follow.
3. Subagents: independent runtime with separate context/artifacts.

There is no single orchestrator that owns:

`phase → required tool calls → subagent execution → validation → retry loop → artifact approval`

This is why user's manual flow works better:

`normal chat → plan → handoff → clean new agent`
