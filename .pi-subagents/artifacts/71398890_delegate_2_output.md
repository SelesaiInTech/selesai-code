## Additional concrete findings

- **medium: docs/workflows.md:139 vs src/extensions/workflow/adapter.ts:134-138** — docs list adapter `toolNames` as `{ start, next, end }`; actual adapter supports `{ start, end }` only. This can make future mode authors configure a nonexistent tool.
- **medium: docs/workflows.md:103-117 vs src/extensions/workflow/package.json:7-10** — docs instruct registering each mode in `pi.extensions`; actual manifest registers one aggregator `./extension.ts`, so following docs could reintroduce duplicate shared-writer registration risk called out in `src/extensions/workflow/extension.ts:1-4`.
- **high: src/extensions/workflow/modes/prototype.ts:77 et al.** — prompt examples use `subagent_type`, not the actual `agent` parameter, likely causing failed or malformed subagent calls unless the model translates the name itself.
- **high: src/extensions/workflow/state-machine.ts:344-350** — terminal auto-close treats any existing `review.md` as sufficient; it does not validate the prompt claim that the commentator reports no outstanding issues.

## Residual risks

- I did not execute the workflow end-to-end, so runtime event ordering issues beyond static evidence are not covered.
- I did not inspect every subagent runtime path; findings focus on the workflow engine and subagent API/output paths relevant to the suspicions.
