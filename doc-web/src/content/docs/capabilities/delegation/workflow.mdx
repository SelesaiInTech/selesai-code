The `workflow` extension ships the four workflow mode shapes as **pi-subagents saved chains**. Four commands are bundled: `/workflow-prototype`, `/workflow-quicktype`, `/workflow-task`, and `/workflow-loop`. Each launches its chain through pi-subagents — phases are chain steps, human gates are `checkpoint` steps, verified acceptance is the chain `acceptance` gate, durable state lives in the auto-created mission, and resumability comes from pi-subagents' retained children.

## Setup and prerequisites

- This extension is bundled with Selesai. It is loaded automatically; you do not need to install it separately.
- It launches chains through the `pi-subagents` extension, which must be loaded (it is bundled too).
- Requires an interactive TUI session.
- The Selesai agent roster (`architect`, `builder`, `commentator`, `explorer`, `recapper`, `researcher`) provides the chain steps.

## What it sets up

- Registers one slash command per mode: `/workflow-prototype`, `/workflow-quicktype`, `/workflow-task`, `/workflow-loop`.
- Each command launches a pi-subagents chain (`launchSlashSubagent`) with the goal as the chain's `{task}`.

### Mode chains

| Mode | Chain steps |
| --- | --- |
| `task` | architect (plan) → checkpoint → explorer (reuse) → recapper (handoff) → checkpoint → builder (implementation, verified acceptance) → commentator (review) → checkpoint |
| `prototype` | researcher (research) → architect (plan) → checkpoint → explorer (reuse) → recapper (handoff) → checkpoint → builder (implementation, verified acceptance) → commentator (review) → checkpoint → commentator (audit of uncommitted diff) |
| `quicktype` | same as `prototype` minus the researcher step |
| `loop` | builder (implementation, verified acceptance) → commentator (review) → checkpoint — direct build↔review rounds for an already-agreed plan |

- Human gates are `checkpoint` steps: approve with `subagent({ action: "approve-checkpoint", id })`, reject with `reject-checkpoint`. A rejected checkpoint stops the chain.
- Builder steps carry a chain `acceptance` gate (verified `checked` level with `commands-run` and `changed-files` evidence).
- Durable process state lives in the auto-created **mission** per launch (state, artifacts, decisions, receipts); inspect with `mission.list` / `mission.show`.
- Resumability is pi-subagents' retained children: `children.list` plus `runs.run({ resume })` to continue a run.

## Commands, tools, and shortcuts

| Command | Description |
| --- | --- |
| `/workflow-prototype <goal>` | Run the full prototype chain (research → plan → reuse → handoff → loop → audit). |
| `/workflow-quicktype <goal>` | Run the quicker prototype chain without research. |
| `/workflow-task <goal>` | Run the task chain (plan → reuse → handoff → build↔review). |
| `/workflow-loop <goal>` | Run direct builder/reviewer rounds for an already-agreed plan. |

## Limits and safety

- Chains launch asynchronously; the live result card, snapshots, and notifications come from pi-subagents' slash UX.
- Each command needs a non-empty goal; an empty invocation shows usage instead of launching.
- The previous durable engine (state machine, `workflow.json` run state, `write_workflow_artifact` / `end_workflow` tools, and marker-validated phase artifacts) is gone. The four modes are chains; phase markers and parent-owned artifact writes are not part of this design.
- Build↔review rounds are driven by the `builder → commentator → checkpoint` segment: a blocking review rejects the checkpoint, and you re-run `/workflow-<mode>` (or resume/append) for another round. There is no automatic iteration cap.

## Migration

Active runs from the old engine (`.selesai/artifacts/*/workflow.json`) are **not resumable**. The old run files can be deleted; start fresh with `/workflow-<mode> <goal>`.
