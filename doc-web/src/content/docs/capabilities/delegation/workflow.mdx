`workflow` is a bundled skill that helps the parent agent orchestrate implementation with `pi-subagents`. It replaces the former `/workflow-*` extension and its fixed, auto-looping pipelines.

Use it inline with `$workflow`, or ask Selesai to orchestrate an implementation. It is a policy layer, not a separate runtime or slash-command system.

## Setup and prerequisites

`workflow` and `pi-subagents` are bundled. No separate installation is required.

## What it sets up

It supplies parent-only orchestration guidance; it does not register a workflow runtime or slash commands.

## What you can configure

The skill has no persistent settings. Adapt the requested flow to the task, then use normal `pi-subagents` controls for delegated runs.

## What you can do

Invoke `$workflow` inline, or ask Selesai to orchestrate the implementation.

## Commands, tools, and shortcuts

Use `$workflow`; coordinated launches use the existing `subagent` tool.

## Limits and safety

The parent remains responsible for scope, acceptance, and deciding when to stop. Keep one writer per checkout.

## How it works

The parent inspects the task first and chooses the smallest safe flow:

| Situation | Flow |
| --- | --- |
| Small, localized change | Implement locally and run a focused check. |
| Bounded implementation | Optional codebase reconnaissance → one writer → focused validation. |
| Uncertain code or external dependency | Reconnaissance and/or research → parent decision or plan → one writer → relevant review. |
| Material architecture or product decision | Resolve the decision first; use an oracle or multiple perspectives only when warranted. |
| Broad or risky work | Serial milestones: decide/plan → one writer → review/validation → scoped fix → re-review if the fix is material. |

The parent remains the decision-maker and final acceptor. Keep one writer per checkout; only independent read-only discovery, research, review, and validation should run in parallel.

## Using delegated stages

The skill uses the `pi-subagents` `workflowScript` API when coordination is needed. Built-in roles can persist concise artifacts such as `context.md`, `research.md`, `plan.md`, implementation reports, and reviews. Pass only the artifacts a later role needs through `reads`; reviewers should inspect the actual current diff.

A handoff is optional. Use one for cross-session continuity, a milestone boundary, or a durable user-facing record—not as a mandatory pipeline stage.

## Review and fixes

For work that merits independent review, define focused acceptance checks before the writer starts. Run only the review lenses that matter to the change, synthesize accepted findings in the parent, then give one scoped fix task to the writer. Re-review only after a material fix. Stop once focused validation is sufficient, no actionable blockers remain, or a user decision is required.

## Migration from `/workflow-*`

The legacy `/workflow-prototype`, `/workflow-quicktype`, `/workflow-task`, and `/workflow-loop` commands were removed. Start a new task with `$workflow` instead. Existing pi-subagents missions and receipts remain available as delegated-work evidence, but they do not make a fixed pipeline authoritative.
