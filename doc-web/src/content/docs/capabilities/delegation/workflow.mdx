The `workflow` extension ships the four workflow mode shapes as **pi-subagents scripted auto-loop workflows**. Four commands are bundled: `/workflow-prototype`, `/workflow-quicktype`, `/workflow-task`, and `/workflow-loop`. Each launches a `workflowScript` through pi-subagents — the mode's phases run as `runs.run` steps, and the build↔review round auto-repeats until the commentator reports clean. A `workflowScript` has no checkpoints, so there are no human gates. Durable state lives in the auto-created mission per launch.

## Setup and prerequisites

- This extension is bundled with Selesai. It is loaded automatically; you do not need to install it separately.
- It launches scripted workflows through the `pi-subagents` extension, which must be loaded (it is bundled too).
- Requires an interactive TUI session.
- The Selesai agent roster (`architect`, `builder`, `commentator`, `explorer`, `recapper`, `researcher`) provides the workflow phases.

## What it sets up

- Registers one slash command per mode: `/workflow-prototype`, `/workflow-quicktype`, `/workflow-task`, `/workflow-loop`.
- Each command launches a pi-subagents scripted workflow (`launchSlashSubagent`) with the goal injected into the mode's `workflowScript`.

### Mode scripts

| Mode | Scripted phases |
| --- | --- |
| `task` | architect (plan) → explorer (reuse) → recapper (handoff) → auto build↔review loop (builder ↔ commentator, until clean) |
| `prototype` | researcher (research) → architect (plan) → explorer (reuse) → recapper (handoff) → auto build↔review loop (builder ↔ commentator, until clean) → commentator (audit of uncommitted diff) |
| `quicktype` | same as `prototype` minus the researcher step |
| `loop` | auto build↔review loop (builder ↔ commentator, until clean) — direct rounds for an already-agreed plan |

- Each mode's phases run as `runs.run` steps inside a `workflowScript`. There are no checkpoints: the script is one-shot-and-sleep, and the commentator's independent review is the loop's gate.
- The build↔review round auto-repeats until the reviewer's output matches the `WORKFLOW_REVIEW_STATUS: clean` marker; `runs.run` keys are unique per round (`build-1`, `review-1`, `build-2`, …).
- Durable process state lives in the auto-created **mission** per launch (state, artifacts, decisions, receipts); inspect with `mission.list` / `mission.show`.
- Workflows launch asynchronously; recover or continue via `mission.list` and the async run `status`.

## Commands, tools, and shortcuts

| Command | Description |
| --- | --- |
| `/workflow-prototype <goal>` | Run the full prototype scripted workflow (research → plan → reuse → handoff → auto loop → audit). |
| `/workflow-quicktype <goal>` | Run the quicker prototype scripted workflow without research. |
| `/workflow-task <goal>` | Run the task scripted workflow (plan → reuse → handoff → auto loop). |
| `/workflow-loop <goal>` | Run a direct auto build↔review loop for an already-agreed plan. |

## Limits and safety

- Workflows launch asynchronously (`async: true`); the live result card, snapshots, and notifications come from pi-subagents' slash UX.
- Each command needs a non-empty goal; an empty invocation shows usage instead of launching.
- The previous durable engine (state machine, `workflow.json` run state, `write_workflow_artifact` / `end_workflow` tools, and marker-validated phase artifacts) is gone. The four modes are scripted auto-loop workflows: the build↔review round is capped at 3, and there are no human gates.
- The old `workflow.json` resume note stays as the migration note: active runs from the old engine are not resumable.

## Migration

Active runs from the old engine (`.selesai/artifacts/*/workflow.json`) are **not resumable**. The old run files can be deleted; start fresh with `/workflow-<mode> <goal>`.
